# Allsolve SDK feedback (QuietOffice)

SDK usability notes, pain points and suggestions found while building QuietOffice.
Kept here so it does not conflict with the shared [docs/sdk-feedback.md](../../docs/sdk-feedback.md); copy rows over when the team merges.

| When | Who | What we tried | What happened | Suggestion |
|------|-----|---------------|---------------|------------|
| 3 Oct | Arman (with Claude) | Find the keyword arguments for the acoustic boundary conditions (`AcousticWavesNormalAcceleration`, `AcousticWavesAcousticDamping`, `AcousticWavesAbsorbingBoundary`) | The acoustics skill only covers transducers and PML. The SDK reference page is one very long page, so the entries were out of reach. We had to read `src/allsolve/physics/generated/interactions.py` on GitHub. The generated docstrings repeat the parameter name ("acoustic waves normal acceleration") with no unit or meaning | One reference page per physics, and docstrings with unit and sign convention. A room-acoustics example (source + absorbing walls + probe points) next to the PMUT one |
| 3 Oct | Arman (with Claude) | Drive a harmonic acoustic simulation with `AcousticWavesNormalAcceleration` set to a constant (`"accel"`) | Mesh and simulation both finished with status SUCCESS, and every pressure output was exactly 0.0. No warning anywhere. A constant is the DC harmonic, so the fundamental is silent; the value has to be `accel * sn(1)`. The RF skill mentions this for magnetics ("drive MUST be AC") but nothing says it for acoustics. It cost several runs that looked fine and produced nothing | Warn, or fail, when a harmonic simulation has no excitation at the fundamental. Say it in the acoustics docs and in the parameter's docstring |
| 3 Oct | Arman (with Claude) | Run a layout search as several sweeps at once from Python threads on one project (`client.in_thread()`) | Worked first time: four mesh jobs and four simulations in parallel, 13 layouts in about a minute. Sweep child jobs show up in the job log with their variable values, which made a good progress display | Nothing to fix. Worth an example in the docs, it is a strong selling point |
| 3 Oct | Arman (with Claude) | Find out how many layouts fit in 30 s, and how sweep steps are run in parallel | The skills say "always prefer sweeps" but not how a sweep runs. Only the `num_replicas` docstring in `resource_reservation.py` says it: one machine per sweep step, at most 100 at once. Measured in 2D: the solve takes 4 to 7 s, but each job first waits in "Reserving resources..." for 14 s (8 machines) to 35 s (100), once for the mesh and again for the simulation. Splitting 67 layouts over 8 sweeps from threads was slower than one sweep (130 s against 84 s). A reservation of `CORES_3_10GB_FAST_START` ended as `failing` with no reason; the default node worked. With 100 machines reserved beforehand, 67 layouts (134 solves) took 21 s. Making the screens a density expression in x and y instead of geometry (one mesh for all layouts) raised that to 200 layouts (400 solves) in 31 s, within 0.1 dB of the remeshed model | Document the sweep execution model and the boot time per machine count in the simulation skill. Say which node types can be reserved, and give a reason when a reservation fails. Let one job mesh and solve, so a sweep waits for machines once |
| 3 Oct | Arman (with Claude) | Set up credentials by following the docs | The SDK skill says `ALLSOLVE_ACCESS_KEY` / `ALLSOLVE_SECRET_KEY`, the example app uses `QS_ACCESS_KEY` / `QS_SECRET_KEY` | Pick one naming and use it in both |
| 3 Oct | Arman (with Claude) | Use the beer-cooling app as the template for our backend | It uses the older style: a config dict into `import_project()` plus a hand-written solver script. The skills teach the builder API (`geometry_builder`, `PhysicsSet`, `create_simulation_harmonic`) and warn off some of what the example does | Update the example app to the current API, or say at the top which style new projects should copy |
